## 补充 2 · 修子进程限制检测逻辑（原判成「未确认已解除」）

### 背景/问题
- 实机反馈：子进程限制页显示「未确认已解除」，但本机实际**已解除**（`device_config max_phantom_processes=2147483647`、`settings_enable_monitor_phantom_procs=false`）。

## 补充 4 · 子进程限制检测改渐进式（Shizuku 优先，诚实 Unknown）

### 背景/问题
- 用户实测：子进程限制页仍显示「未确认已解除」，问「需要 adb？」。
- 结论：**Android 无公开 API 读子进程限制**（`MAX_PHANTOM_PROCESSES` 是 `ActivityManagerConstants` 内部字段，不对应用层暴露）。普通 App 无 root/adb 时，唯一公开入口 `Settings.Global` 那个 feature flag 在多数国产 ROM 读出 null，**无法可靠读取**。
- codetool 独特优势：**内置 Shizuku**（shell uid 2000 = 免 root 的 adb），可跑 `dumpsys activity settings` 解析——这是没 root、没手动连 adb 时唯一稳定的读取路径。

### 改动
- `shizuku/ShizukuBridge.kt`：新增公开 `execShell(cmd)`（包一层现成 `execViaShizuku`），供 App 内需特权、用户已开 Shizuku 的场景调用（内部轮询阻塞 ≤3s，调用方须后台线程）。
- `SubprocessLimitActivity.kt`：检测改**渐进式**（sealed `PhantomState`：Unrestricted / Limited / Unknown）：
  ① Shizuku 跑 `dumpsys activity settings`，宽松正则解析 `max_phantom_processes`（namespace 兼容 activity_manager/activity）；=2147483647 → 已解除，小数字 → 仍受限。
  ② 降级 Settings.Global 试探（monitor 开关 / max 值）。
  ③ 都读不到 → `Unknown`，诚实显示「无法自动检测（需 Shizuku 或 root）· 可开 Shizuku 自动检测或开发者选项确认」，不假装知道。
  检测放 `lifecycleScope + Dispatchers.IO`（dumpsys/Shizuku 阻塞），结果回主线程 `renderState` 上色（绿=已解除/橙=受限/灰=未知）。

### 验证
- 编译 BUILD SUCCESSFUL。实机走查待验证（设备无线 adb 仍连不上）：需在已开 Shizuku 的设备上确认能解析出 max_phantom_processes 并正确显示状态。

### 高亮方案调研（查证后用）
- sora-editor 0.23.6 时代官方配套语言模块只有 `language-textmate`（VSCode 同款 TextMate grammar/主题）和 `language-treesitter`（需 native 库，重）。
- 选 textmate：`io.github.Rosemoe.sora-editor:language-textmate:0.23.6`；minSdk 26 < 33 必须开核心库去糖（`isCoreLibraryDesugaringEnabled = true` + `desugar_jdk_libs:2.1.5`）。
- 语法文件（VSCode 同款 .tmLanguage.json）从 VSCode / eclipse-tm4e language_pack 下载，4 种语言注册进 `assets/textmate/languages.json`：markdown（text.html.markdown）、shell（source.shell）、json（source.json）、jsonc（source.json.comments）。

### 改动文件
- `app/build.gradle.kts`：+language-textmate 依赖、+核心库去糖配置。
- `assets/textmate/`（新）：languages.json + markdown/shell/json/jsonc 的 .tmLanguage.json + language-configuration.json + 主题 darcula（深色）/ quietlight（浅色，官方 Demo 验证过的 tm4e 原生格式）。
- `util/TextMateEditor.kt`（新）：初始化封装——Application.onCreate 一次性加载语法+双主题（幂等）；`applyTo(editor, path)` 按文件后缀选 scope + **按 app 主题选 TextMate 主题**（浅色→quietlight、深色→darcula，用 ThemeManager.currentMode）；colorScheme 只建一次 + setTheme/invalidate（官方 Demo 模式）；失败走 FileLog 留痕不崩编辑器。
- `CodeToolApp.kt`：onCreate 调 TextMateEditor.init。
- `SkillEditorActivity.kt`（.md）、`ConfigEditorActivity.kt`（.json/.jsonc）、`ScriptEditActivity.kt`（.sh）：加载文本后 applyTo 设高亮（必须**先 setText 再 applyTo**，语言异步加载会清空正文）。
- `MainActivity.kt` showFontSizeDialog：挂载目录 RadioGroup 改 Spinner 下拉框（根因：动态 addView 的 RadioButton id 都为 0，RadioGroup 互斥判 id 失效出现双选中）。
- 宿主机 dev-conventions skill：新增「第三方编辑器/语法高亮库的配色必须跟随 app 主题（强制，真实踩坑）」；同步内置 DEV_BODY（注意：宿主文本不能出现 `"""`，python 同步只转义 `$`，三引号会截断 Kotlin raw string）。

### 关键实现 / 踩坑
- **主题格式**：VSCode 的 `colors`+`tokenColors` 格式在 tm4e 里 tokenColors 不会映射成上色表（token 不上色）；必须用官方 Demo 同款 tm4e 原生格式（`settings` 数组）——darcula/quietlight 实测 token 上色成功。
- **JSONC 主题**：VSCode 主题带 `//` 注释+尾逗号，tm4e/Gson 解析抛 MalformedJsonException，需 Jsonc.stripComments+stripTrailingCommas 预处理；include 的 _vs.json 是 tm4e 内部加载无法预处理，直接在 assets 源头洗净（或用无 include 的官方主题）。
- **先 setText 后 applyTo**：TextMate 语言加载异步，先设语言会清空已渲染正文（正文区全空，只有行号）。
- **colorScheme 只建一次**：每次重建会让 Analyzer 持有的 theme 引用与 colorScheme 不一致，token 颜色映射失效（官方 ensureTextmateTheme 模式）。
